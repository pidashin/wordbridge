# Word Runner — Feature Spec (Wordbridge)

Draft · 2026-10-19 · based on `word-runner-game-spec.md` (Johnny), adapted to
the wordbridge codebase.

A one-button side-scrolling runner inside wordbridge. The character runs
automatically; the player jumps to collect letters in order and spell
vocabulary words from the wordbridge word list before a timed round ends.

## 1. Goals and non-goals

**Goals**

- Add a new way to practise the *same words* the exam uses, focused on
  **spelling** (the exam is multiple choice).
- Playable end to end on desktop and phone: title → round → result.
- Feed results back into the existing per-user mistake tracking, so spelling
  trouble shows up in the 錯題本 (mistake review) exam mode.
- Quick demo first: **one visual theme**, built so more can be added as data.

**Non-goals (v1)**

- Per-word images, accounts/leaderboards, multiplayer, power-ups, user-made
  word lists, native builds, a test framework.
- Any database schema change, Docker/deploy change, or new infrastructure.

## 2. Decisions already made

| Topic | Decision |
| --- | --- |
| Themes | v1 ships **one** theme (a background look). More themes later, switched randomly each time the target word changes. |
| Word source | **Demo phase (decided 2026-10-19):** a small built-in list (~20 words incl. `apple`), random order, no database or GraphQL needed, behind a `USE_DEMO_WORDS` flag. Later: the wordbridge `Word` table via the `words` query (§5); no theme/category field needed. |
| Images | None per word. Game art is generated by Claude as SVG (see §8). |
| Engine | Phaser 4 (see §9 for why). |
| Location | New route `/runner` inside the wordbridge Next.js app. |

## 3. Player experience

1. Home page (user already picked) shows a **Word Runner** button next to
   *Start Exam*.
2. **Title screen:** pick a word source — *All words* or *My mistakes*
   (disabled without a user, or with fewer than 5 mistake words) — Start.
3. **Round:** 180 s countdown. The character auto-runs right. The HUD shows
   the target word as slots (`a p _ _ _`) **plus its Chinese meaning**
   (`zhTW`), because the learner spells from the meaning.
4. Touch the next needed letter → it fills the slot. Touch any other letter →
   −1.5 s, red flash, shake. Complete the word → celebration, the next word
   starts.
5. **Result:** words completed, each spelled word with its meaning, wrong
   letters hit, best score (saved in the browser), Play again / Back home.

## 4. Gameplay rules

### Controls

| Input | Action |
| --- | --- |
| Space / Up / click / tap | Jump |
| Hold | Higher jump (variable height, capped) |
| P / Esc | Pause (resume, restart, quit) |

Single jump only in v1 (double jump = config flag, default off).

### Terrain, platforms and gaps (revised 2026-10-28)

- **The ground is flat** (one baseline height, no hills or slopes). The
  parallax background hills stay; only the running route is flat.
- The route is chunks joined end to end, Mario-style:
  - **flat** run (plain ground, optionally with a low block to jump over);
  - **gap** (a hole in the ground the player must jump over);
  - **platform** (a raised ledge: jump up onto it, then jump again to reach
    a letter above it). Platforms are one-way (you can jump up through them
    and land on top). Optionally a two-step staircase of platforms.
- **Falling into a gap = respawn, not failure.** When the character falls
  below the ground it respawns on the solid flat ground **behind the gap**
  (the side it came from, at a safe spot clear of blocks and platforms), with
  a short respawn effect (e.g. sparkle ring / pop-in) and ~1 s of blinking
  invulnerability. No time penalty and no lost letters (the lost run time is
  the cost). Every gap is preceded by enough plain flat ground to always have
  a safe respawn spot.
- Hitting a block still only slows the character (speed ×0.4 for ~0.8 s).
- **Reachability invariant (every generated stretch):**
  - a gap is clearable at base speed with a normal jump (width ≤ ~70% of the
    shortest jump's airborne distance, plus a little coyote time for
    forgiveness);
  - a platform top is reachable with a normal jump (height ≤ ~60% of the max
    jump apex); a staircase step likewise relative to the step below;
  - every letter is collectable: letter height above the surface it belongs
    to (ground, platform top, or the arc over a gap) ≤ ~80% of the max jump
    apex measured from that surface;
  - platform letters sit high enough that you need to be *on* the platform
    (second jump) to get them.

### Spelling

- Strictly left to right; only the **next needed letter** counts.
- Repeated letters (apple → p, p): each pickup fills exactly one slot.
- Any other letter — including one needed later in the word — is a
  distractor: costs time, changes no slots.
- Correctness is decided **at touch time** against the then-current target
  (a distractor on screen may become the right letter after a fill).
- Letters are lowercase.

### Letter spawning

- Letters are **sparse**: the character runs a short stretch before meeting
  the next letter (target spacing about 450–800 px, roughly 1.5–3 s of
  running at base speed; tunable). Letters do not come in dense clusters.
- Letters spawn lazily about 1.5 screen widths ahead of the player.
- A pickup that is still beyond the right screen edge is **provisional**:
  when the target changes (slot filled or new word), the spawner may rewrite
  provisional letters so the current target letter always appears at least
  once in the next ~2 screen widths (with sparse letters, make the next
  letter the target if needed).
- Distractors are 40–60% of spawned letters (tunable). Look-alike/sound-alike
  bias (b/d, p/q) is a later difficulty option.
- Placement: on the ground at a low height, in the arc over a gap, and above
  platforms (needs the second jump). Never inside solid ground or blocks.

### Timer and scoring

| Setting | Default |
| --- | --- |
| Round length | 180 s |
| Wrong letter | −1.5 s |
| Correct letter | 0 s |
| Word completed | +1 word (optional +3 s bonus, off) |
| Obstacle / pit | slowdown only |
| Run speed | 280 px/s, optional small ramp per completed word |
| Score | Words completed; tie-break fewer wrong letters |

All values live in one `config.ts` so playtests only change numbers.

## 5. Content: the word pool

Source: `words` query (`enUS`, `zhTW`). Normalise and filter:

- lowercase + trim; keep only `/^[a-z]{3,8}$/`; de-duplicate.
- This drops hyphenated and multi-word entries (`roller-skate`, `look for`).
  Against the seed data (617 words) about 529 qualify.
- Minimum pool of 5; otherwise the title screen shows a message instead of
  starting.
- Words are drawn at random without repeating within a round.

*My mistakes* source: `mistakeWords(userId)` through the same filter.

## 6. Wordbridge integration

- **User:** reuse the localStorage keys `wordbridge_user_id` /
  `wordbridge_username` (same as the home page and exam). Playing as guest is
  allowed for *All words*; nothing is recorded for guests.
- **Progress write-back:** when a word is **completed**, call the existing
  `recordAnswer` mutation once with `correct = (wrong letters on this word
  === 0)` and `isMistakeReview = (source === 'mistakes')`. Words abandoned at
  timeout record nothing. No new GraphQL fields, no schema change.
- **Best score:** `localStorage`, key per user (or guest).
- **GraphQL:** new `app/gql/` usage reuses `GET_WORDS`, `GET_MISTAKE_WORDS`,
  `RECORD_ANSWER`; no resolver changes.
- **basePath:** the app is served under `/wordbridge`. Next prefixes routes
  and `next/link`, but Phaser's loader does not — asset URLs must be built
  with `BASE_PATH` from `app/basePath.ts`.

## 7. Themes (data-driven, one in v1)

```ts
type Theme = {
  id: string;
  name: string;
  sky: { top: string; bottom: string };
  layers: { key: string; file: string; scrollFactor: number; y: number }[];
  ground: { key: string; file: string };
};
```

- v1: a single theme, `meadow` (sky gradient, far hills, near hills, clouds,
  grass ground tile).
- `ThemeManager.next()` is called whenever a new target word starts; with one
  theme it returns the same one, so switching is already wired but a no-op.
- Adding a theme later = add art files + one `Theme` entry; no code change.
  Switching between themes crossfades the layers (~400 ms).

## 8. Art (no audio)

**Art — generated by Claude, SVG-first, flat cartoon style, one palette.**

- Files to produce for `meadow`: sky (or CSS gradient), 2 hill layers,
  clouds, ground tile, low block, pit edge, character (4 run frames + jump +
  stumble), simple celebration sparkle.
- Letter pickups, slots, HUD, and particles are drawn procedurally by Phaser
  (rounded bubble + text) — no files.
- SVGs loaded through Phaser at a fixed rasterisation scale; stored under
  `public/runner/`. No external image service, no licensing questions.
- **Checkpoint:** after milestone 1 the user reviews a screenshot of the
  character and background before more art is made. If SVG looks too plain,
  fallback is the Figma image generation tool for raster art.
- Optional later: more word-independent theme sets, per-word emoji on the
  result list.

**No audio.** Decision (2026-10-19): the game has no sound effects, no
pronunciation and no mute toggle.

## 9. Technical design

**Engine: Phaser 4** (latest stable is 4.1.0, April 2026, per
[phaser.io](https://phaser.io/download/stable)). It gives scaling
(FIT, landscape), camera follow, parallax layers, SVG loading, and pointer
input for free, which is most of this game's non-logic code. A hand-rolled
canvas would be lighter but means re-building all of that. The game logic is
kept free of Phaser so the engine stays swappable. *Verify every Phaser API
used against the Phaser 4 docs/changelog before use — v4 differs from v3 in
places; do not rely on v3 examples.*

**Next.js integration**

- `app/runner/page.tsx` — client route; loads the game with
  `next/dynamic(() => import(...), { ssr: false })` so Phaser (browser-only,
  ~1 MB) never touches the server bundle or other pages.
- Game canvas is created in an effect on mount and destroyed on unmount
  (also handles React strict-mode double mount and Next route changes).
- Layout is landscape-first; in portrait show a "rotate your device" overlay.
  Target 60 fps on a mid-range phone.

**Proposed file layout**

```
app/runner/
  page.tsx                  route + dynamic import + data loading (Apollo)
  RunnerGame.tsx            mounts/destroys the Phaser game
  config.ts                 all tunables (§4 table, distractor ratio, ...)
  logic/                    pure TypeScript, no Phaser imports
    wordPool.ts             normalise/filter/dedupe, draw without repeat
    wordProgress.ts         slot state, correct/wrong decision, counters
    letterSpawner.ts        spawn + provisional rewrite rules
    terrainGenerator.ts     chunk chaining + reachability invariant
    roundTimer.ts           countdown + penalties
  scenes/                   Boot, Title, Game, Result (Phaser)
  themes.ts                 Theme type + meadow entry
public/runner/              SVG art
```

Modules map to the original spec: `WordManager` → `wordPool` +
`wordProgress`; `Player` lives in the Game scene; `HUD` in the Game scene.

**No new dependencies except `phaser`.**

## 10. Acceptance criteria

1. `/runner` loads from the home page link and works under the `/wordbridge`
   base path; other pages do not load Phaser.
2. A full round (title → ≥ 3 completed words → result) works with mouse,
   keyboard, and touch emulation.
3. Spelling rules in §4 hold, including repeated letters (e.g. `apple`) and a
   distractor that equals a later letter.
4. Over a 3-minute round the target letter is never absent for more than ~2
   screen widths, and every letter is reachable (checked by a logged
   simulation of the generators — see §11).
5. Wrong letter: −1.5 s with feedback; obstacle/pit: slowdown only.
6. Result screen lists spelled words with `zhTW`; best score persists across
   reloads.
7. For a signed-in user, completing a word calls `recordAnswer`; a word with a
   wrong letter appears in *My mistakes* afterwards and in the exam's mistake
   review mode.
8. Guest mode records nothing and does not error.
9. `npm run build` and `next lint` pass; browser console has no errors during
   a full round.
10. Empty/short pool (< 5 words) shows a message, not a broken game.

## 11. Verification plan

The repo has no automated tests and this spec does not add a test framework
(ask first if that is wanted). Verification is:

- `npm run build` and `next lint`.
- The pure `logic/` modules are exercised by a throwaway script (run with
  plain Node/tsx from a scratch dir, not committed) that generates many
  rounds and asserts the reachability, target-frequency, and spelling
  invariants.
- Manual run in the dev server: desktop viewport, then phone landscape
  emulation; one full round each; check the exam's mistake review after a
  signed-in run.
- A human look at the art and game feel — the checker cannot judge these; the
  flow stops and asks the user.

## 12. Milestones

1. **Prototype:** route, Phaser mount/unmount, auto-run, jump, flat ground,
   camera follow, `meadow` background + character art
   (**art checkpoint**).
2. **Letters:** word pool, one word, spawner, slot + meaning HUD, wrong-letter
   penalty.
3. **Full round:** countdown, multiple words, title + result screens, pause,
   best score.
4. **Integration:** home page button, *My mistakes* source, `recordAnswer`
   write-back, guest handling.
5. **Polish and tuning:** mobile feel, difficulty numbers, terrain variety.
6. **Later:** more themes (random per word), per-word emoji/images, look-alike
   distractors, difficulty tiers, daily challenge.

Each milestone is one feature branch / PR if it is large enough to review on
its own; otherwise 1–3 can ship as one PR.

## 13. Boundaries (from the project rules)

- Public repo: no secrets, no `.env*`, no database files, no real user data,
  no infrastructure details in code, commits, or PRs.
- Stop and ask before touching `prisma/schema.prisma`, the Dockerfile,
  compose, or any deploy config. This feature is designed to need none of
  them.
- Never run Docker locally. The production image is not built as part of this
  work; deploying is a separate, explicit request.
- Branch → commit → PR; the user merges.
